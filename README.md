# af2-server

Неофициальный сервер для клиента Atom Fishing 2, написанный на Rust. Официальные
серверы игры выключены 01.08.2023, исходники сервера не публиковались, поэтому
протокол восстановлен по клиенту.

Проект не связан с разработчиками и издателем игры. В репозитории нет кода и ресурсов
игры: описания предметов каждый извлекает из своей купленной копии. Таблица рыбы
`config/fish.json` собрана по архивным гайдам игроков в Steam «Водоёмы, обитатели,
наживки, ресурсы» и «Клевалка от Элиаса».

Сервер рассчитан на нескольких игроков, но играть вместе пока нельзя: игроки не видят
друг друга. **Открывать его в интернет пока рано**, см. раздел «Вход и безопасность».

## Как это работает

Клиент говорит по Photon (TCP, порт 9201, имя приложения `AFCServer`), но всю игровую
логику гонит через **два Photon op-кода** со своим бинарным форматом внутри:

```
op 0:  { 0: msgId, 7: (counter + msgId) ^ -124,       2: counter, 5: payload }
op 1:  { 1: msgId, 4: (counter + msgId) ^ 0x0A937F7F, 2: counter, 3: payload }
сервер -> клиент (event / operation response):  { 1: msgId, 3: payload }
```

`payload` — обычный little-endian `BinaryWriter`; строки это `int16` длина + UTF-8.

Слои в коде:

| Файл | Что делает |
|---|---|
| [src/photon.rs](src/photon.rs) | Кадры Photon по TCP и Protocol16 (big-endian) |
| [src/afc.rs](src/afc.rs) | Конверт AF2, чтение и запись игрового payload |
| [src/server.rs](src/server.rs) | Задача на соединение, журнал неотвеченных сообщений |
| [src/world.rs](src/world.rs) | Общее для всех соединений: настройки, хранилище, кто в игре |
| [src/game/](src/game/) | Правила игры, по файлу на систему |
| [src/storage/](src/storage/) | Типаж `Storage` и его реализация на SQLite |

Каждым персонажем владеет задача его соединения, поэтому игровому коду не нужны
блокировки. Если персонажа открыли со второго соединения, первое закрывается.

## Установка для игрока

Нужна купленная Atom Fishing 2, установленная через Steam.

1. Скачай архив из [Releases](https://github.com/kvirund/af2-server/releases) и распакуй его.
2. Запусти `af2-launcher.exe` и выбери сервер: локальный, из списка или свой адрес.
3. Игра запустится сама. При локальном сервере не закрывай окно лаунчера: сервер
   остановится вместе с игрой.

Устанавливать ничего больше не нужно. При первом запуске лаунчер сам прочитает описания
предметов из установленной игры и сохранит их в `data/items.json`. Эти данные принадлежат
игре, поэтому в репозиторий и архив они не входят.

Чтобы запускать из библиотеки Steam, добавь `af2-launcher.exe` как стороннюю игру.
В параметрах запуска можно указать `--server local`, и меню не появится.

Лаунчер записывает адрес сервера прямо в `Assembly-CSharp.dll` и проверяет его при каждом
запуске, поэтому проверка файлов в Steam ничего не сломает. Вернуть исходный адрес:
`af2-launcher --restore`, показать текущий: `af2-launcher --status`. Список серверов
в меню задаётся в `config/launcher.json`.

## Запуск для разработки

Нужен [Rust](https://rustup.rs/). Лаунчер подготовит клиент и запустит сервер, игру оставит закрытой:

```bash
cargo run --release --bin af2-launcher -- --server local --no-launch
```

После первой подготовки сервер можно запускать отдельно:

```bash
cargo run --release -- --trace trace.log
```

Отдельно запущенный сервер слушает `0.0.0.0:9201` и пишет каждое входящее сообщение;
локальный сервер из лаунчера доступен только с этого компьютера. Прогресс лежит в
`data/af2.sqlite`. Параметры: `--config <папка>`, `--db <файл>`, `--bind <ip>`,
`--port <n>`, `--trace <файл>`.

## Вход и безопасность

Клиент сам сообщает свой SteamID, и сервер пока ему верит: зная чужой SteamID, можно
войти в чужой аккаунт. Steam-билет клиент не отправляет, поэтому проверить его нельзя.

Клиент умеет показывать окно PIN-кода: сервер отвечает на вход статусом `PIN`, и клиент
повторяет запрос с кодом. Для открытого сервера подойдёт такая схема: сайт подтверждает
SteamID через Steam OpenID и выдаёт PIN, а сервер проверяет его и ограничивает попытки.

Уровни, принадлежность персонажа и предметов сервер проверяет сам.

## Хранилище

Игровой код работает только с типажом `Storage`. Сейчас есть SQLite в режиме WAL: одна
запись за раз, чего хватит на десятки игроков. PostgreSQL понадобится, если сервер
будет работать в нескольких процессах, и потребует ещё одной реализации типажа.

## Подготовка клиента

Всё делает лаунчер. Клиент выбирает адрес одной строкой в `Assembly-CSharp.dll`.
Сборка не подписана, поэтому строку можно заменить на месте: новый адрес не длиннее
исходного (26 символов), а порт в клиенте всегда 9201. Другой способ — запись в файле
`hosts` для `gamesrv1.af2.cryptodev.app`, он пока не проверялся.

> **Про `isLocalServer`.** В клиенте есть дев-переключатель на локальный сервер, и в
> реестре даже лежит `HKCU\Software\R-Age\AFCGame\isLocalServer_h2848998327`. Но
> ставить его **бесполезно**: обфускатор переставил строковые литералы между
> методами-пустышками, и ключ настройки, который реально читается в рантайме, —
> не `isLocalServer`. Проверено: флаг стоит 1, а клиент всё равно идёт на
> прод-адрес. Поэтому патчится именно прод-слот, и флаг больше не нужен.

**Запуск.** Только через Steam (`steam://rungameid/557780`). При прямом запуске
`AFCGame.exe` Steamworks не поднимается (`SteamAPI_Init() failed`), и игра
требует запустить клиент Steam.

**Что можно добыть** — `tools/reachability.py` проверяет, какие предметы игрок может
получить на этом сервере (магазины, стартовый набор, улов, сбор, рецепты с доступными
рецептами и ингредиентами), и для остальных пишет причину. Нужны `data/items.json` и
`data/recipes.json`, которые делает лаунчер:

```bash
python tools/reachability.py "C:/Program Files (x86)/Steam/steamapps/common/AF2" data/reachability.md
```

**Нажатия в окне игры** — `tools/ui.ps1` (скриншот и клик через user32):

```bash
powershell -File tools\ui.ps1 -Action shot -Out shot.png
powershell -File tools\ui.ps1 -Action click -X 968 -Y 545
```

Две грабли, обе стоили времени:

- Скрипт требует, чтобы окно игры было на переднем плане, и восстанавливает его:
  полноэкранное окно Unity само сворачивается при потере фокуса. Без этой проверки
  легко снять скриншот или кликнуть в чужое приложение — один раз так и вышло,
  скриншот поймал другую запущенную игру.
- Клики через `mouse_event` срабатывали не всегда, причина неизвестна. Скрипт
  использует `SendInput` с абсолютными координатами.

**Фокус забирает только `-Action click` и `-Action focus`.** `shot` намеренно этого
не делает и просто откажется снимать, если окно игры не на переднем плане: утащить
окно под руками у человека, который работает за этой же машиной, — худшее, что может
сделать отладочный скрипт.

Для обычной отладки берите `PhotonProbe` — он не трогает ни окно, ни фокус. Игра
нужна только чтобы проверить разбор на стороне клиента.

## Проверка без игры — основной способ отладки

`tests/PhotonProbe` — это **настоящая** библиотека Photon из клиента
(`Photon3Unity3D.dll`), натравленная на наш сервер. Она повторяет весь обмен логина,
поэтому сервер можно крутить **не запуская игру**: ни окна, ни перехвата фокуса,
ни кликов.

```bash
dotnet run --project tests/PhotonProbe/PhotonProbe.csproj -- 127.0.0.1:9201 my-test-account
```

Ожидаемый вывод:

```
[status] Connect
-> msg 90    <- event msg 90, 8 bytes   02 00 4F 6B 01 00 00 00
-> msg 105   <- event msg 105, 28 bytes 50 C3 ... EA 07 0B 00 08 00
-> msg 110   <- event msg 110, 69 bytes ... персонаж ...
             <- event msg 111, 0 bytes
```

Живой клиент нужен только для проверки того, что он сам парсит ответы — как с
blob'ом внешности, падение которого нашлось именно так.

### Живой обмен

```
[c1] connected from 127.0.0.1:60468
[c1] init request, application = "AFCServer"
[c1] <- msg 90 via op1, counter 1, checksum ok, 87 bytes
[c1]    LOGIN REQUEST  marker=1731 login="" password=<empty>
        steamId="<SteamID>" persona="<имя в Steam>" steamLogin=True pin=0
[c1]    -> LOGIN OK (account 1)
[c1] <- msg 255 ...   <- ровно те три сообщения, которые
[c1] <- msg 105 ...      клиент шлёт после успешного логина
[c1] <- msg 110 ...
```

`msg 255` с нулевым int приходит и дальше каждые 10 секунд — это heartbeat.

### Что известно про сообщения

| id | Направление | Содержимое |
|---|---|---|
| 90 | клиент → сервер | `Int64 marker` (1731), login, password, steamId, deviceId, persona, `Bool` steamLogin, `Int32` pin |
| 90 | сервер → клиент | `String` статус (`"Ok"` или `"PIN"`); при `Ok`: `Int32` id аккаунта, `String` токен привязки, `Int32` флаг |
| 255 | клиент → сервер | heartbeat, `Int32 0`, раз в 10 с |
| 105 | клиент → сервер | запрос валюты; ответ — два `Int64` |
| 110 | клиент → сервер | запрос списка персонажей |
| 110 | сервер → клиент | записи подряд до конца payload: `Int64` id, `String` имя, `Int32` уровень, `Int32` костюм, `Int32` baseId, `Int32` locId, `Int64`, `Int32` длина + blob внешности |
| 111 | сервер → клиент | пустой payload; клиент делает `SceneManager.LoadScene(1)` → экран выбора персонажа |
| 87 | клиент → сервер | строка со steamId — кнопка «Привязать аккаунт к Steam» |
| 1005 | клиент → сервер | 96 байт из `Fisherman.cs` — состояние и позиция игрока, раз в ~3 с |
| 60 | клиент → сервер | 16 байт из `ActiveObject.cs` — взаимодействие с объектом на базе (NPC) |
| 100 | клиент → сервер | `Int64` id персонажа — кнопка «В игру» (`SelectShadowLogic.goToGame`) |
| 145 | сервер → клиент | каталог баз, записи подряд до конца: `Int32` id, 4×`Int32`, `Bool`, 2×`Int32` |
| 150 | сервер → клиент | `Int32` baseId, затем детали базы и её локации (см. ниже) |
| 151 | сервер → клиент | пустой payload, `LoadScene(4)` — база. **Это ответ на кнопку «В игру».** |
| 112 | сервер → клиент | `Int32`, затем `LoadScene(2)` — **редактор персонажа**, не локация |
| 157 / 160 | сервер → клиент | `Int32` baseId, `Int32` locId, `Int32`, `Int32`. `locId == 0` → база; иначе водоём (157 через менеджер локаций, 160 грузит сцену 6 напрямую) |

### Сцены билда

Список берётся из `globalgamemanagers`, а не из догадок — я один раз предположил,
что сцена 2 это водоём, отправил 112, и клиент ушёл в редактор персонажа:

```
0 MainMenu    1 SelectShadow   2 CreateShadow    3 Loc3DStyle   4 Base
5 Loader      6 Loc3DStyle     7 AddSceneSklad   8 UserCheat    9 GlobalMap
```

```bash
strings -a AFCGame_Data/globalgamemanagers | grep '\.unity$'
```

**Токен привязки в ответе на логин обязателен.** Формально это поле необязательное —
клиент читает его только если в payload ещё остались байты. Но если его не прислать,
`JBEHMPDDMME.AMJCBLPKNCB` остаётся пустым, и `SelectShadowLogic.checkPriv()` решает,
что аккаунт не привязан к Steam:

```csharp
if (AMJCBLPKNCB == "") { steamConnectBtn.SetActive(true);  toGameKey.SetActive(false); }
else                   { toGameKey.SetActive(true);        steamConnectBtn.SetActive(false); }
```

То есть кнопка «В игру» просто не появляется, вместо неё висит «Привязать аккаунт
к Steam», и из экрана выбора персонажа выхода нет. Сервер отдаёт в токене тот
steamId, который клиент прислал в логине.

Полезно на будущее: `checkPriv` размножен обфускатором в 15 клонов с переставленными
`true`/`false`. Настоящий — тот, которому оставили читаемое имя; остальные мусор.

**Одного 151 мало.** Сцена Base загрузится, но будет каждый кадр падать в
`LocNewLogic.Update()` и `Fisherman.Update()` — чёрный экран. 151 только грузит
сцену, а текущую базу выставляют данные локаций. Порядок обязателен:

```
145  каталог баз          -> заполняет словарь
150  детали базы          -> индексируется в этот словарь, иначе KeyNotFound
151  загрузить сцену
```

`EDLNGHBMJBL.AADJMFJMAGF` ищет локацию по паре (baseId, locId) персонажа. У нашего
персонажа locId = 0, поэтому **локация с id 0 должна быть в сообщении 150** —
иначе поиск вернёт null и начнутся те же NRE.

Детали базы (`LKDIADGGOLN.CPKLGCKGHFN`): `Bool`, 3×`Int32`, `Bool`, `DateTime`
(6×`Int16`), `Int32` число локаций, и на каждую — `Int32` baseId, `Int32` locId,
затем `Int32`, `Int32` mapX, `Int32` mapY, `Bool`, `Bool`, `Int32`, `Int32`.

Базы лежат в `StreamingAssets/Windows/bases/base_N`, так что id базы должен быть
из реально существующих (1..9).

**Blob внешности** (`Character.initShadowsParams`) — плоский набор байт, каждый индекс
в палитре `Customizator`. Первые 17 читаются безусловно, более короткий blob роняет
экран выбора персонажа через `EndOfStreamException`:

```
[0]      1 = мужчина, иначе женщина
[1]      цвет волос
[2..3]   цвет верха, цвет низа
[4..5]   камуфляж верха, камуфляж низа
[6..9]   верх:  intensive, scale, rotate, hue
[10..13] низ:   intensive, scale, rotate, hue
[14..16] читаются и выбрасываются
дальше опционально: борода, усы (bool)
```

## Карта протокола в клиенте

Декомпиляция (`ilspycmd`, dotnet global tool) обфусцирована Beebyte — имена переименованы,
но строки целы и код читается:

| Класс | Роль |
|---|---|
| `NJMHLCGIAJI` | Сетевой слой: `OnEvent`, `OnOperationResponse`, обёртки op 0/1, `Connect` |
| `EMJAJDNLEJN.FIDCELLHJIH` | Диспетчер входящих: switch на 192 типа сообщений |
| `HBPNMNGOFMA` | Reader игрового payload |
| `EPMPHJGALBE` | Writer игрового payload |
| `IFPIMPMKJIB` | Адрес сервера, версия клиента, порт 9201 |
| `HPGKIJLKCIH` | Настройки, флаг `isLocalServer` |

Полезное про обфускатор: он размножает методы-пустышки и переставляет строковые литералы
между ними, так что часть веток — мусор. Настоящую видно по тому, кто её вызывает.

## Переход на локацию, инвентарь, неотвеченные сообщения

- C→S 138: `Int32 base, Int32 loc, Int32 point`. Шлют `LocButton`, двери и `Fisherman`
  при падении в воду. Ответ: 158 (точка), затем 160 (сцена 6, для `loc == 0` сцена 4).
  Локация обязана быть в сообщении 150, иначе клиент пишет `No location found`.
- C→S 139: те же поля, от зоны `ToLocZone` с `softSpawn` на краю локации, которая ведёт в соседнюю в той же сцене (Мост → Склон на лодочной базе). Ответ: 157 (int база, локация, 0, 0) — клиент переключает локацию без загрузки сцены, показывает её название и шлёт 1007.
- S→C 100: полный персонаж. S→C 180: предметы (формат в `src/game/inventory.rs`).
- Слоты из блоков `bag=` в `resources.assets`: сумка 100 (поплавочная) это 1 удочка,
  2 катушка, 3 леска, 4 поплавок, 5 прикорм, 10 крючок, 20 наживка; сумка 60, ячейка 6 садок.
  Без садка клиент считает его переполненным.
- Всё, на что сервер не ответил, пишется в лог строкой `UNANSWERED` (первый раз за
  соединение с пометкой `NEW`), при отключении клиента выводится `UNANSWERED SUMMARY`.

## Рыбалка

- C→S 1120 раз в 5 с, пока наживка в воде. Ответ S→C 1120: `false + float` или поклёвка
  (формат в `src/game/fishing.rs`). Вываживает клиент сам.
- C→S 1130 (индекс удочки) → S→C 1130 с рыбой. C→S 1135/1136 (id рыбы) → S→C 1135 с опытом.
- `config/fish.json` собирает `tools/gen_fish.py` из архивных копий гайдов игроков в Steam:
  виды по локациям, пороги «маленькая / крупная / трофей», наживки, правила глубины и ночи.
  Шанс клёва, доли видов и размерных классов, верхний вес (1,5 трофейного), параметры
  вываживания и опыт нигде не записаны и заданы в `config/settings.json`.
- Привлекательность наживки, насадки или блесны (первое число `basePar`, норма 100) умножает шанс поклёвки, и сонар показывает уже его. Что она влияет на клёв, сказано в описании предметов клиента; сам множитель придуман (`fishing.baitAttraction`, 0 выключает).
- Клиент подтягивает уставшую рыбу силой катушки, а фрикцион сам ставит на 80% от самой слабой
  части снасти, поэтому рыба тяжелее снасти почти не идёт. Сервер даёт рыбу не тяжелее
  самого слабого теста удилища, катушки и лески × `fishing.tackleWeightFactor` (1,5 по гайду
  Элиаса); вид, который мельче этого не бывает, на такую снасть не клюёт.
- Номер локации приходит только в C→S 138, поэтому сервер запоминает его для 1120.
- Поле размера в 1120 — доля 0..1 между мин. и макс. моделью; поле качества в 1130 — класс 0..2.
- Игровое время клиент считает по часам ПК; 12 игровых часов за реальный взят из гайда.
- Вес крючка входит в скорость погружения: у крючка «Гладь-20-0» он равен -8, снасть
  с ним всплывает и поплавок лежит.
- Запрос без ответа может оставить чёрный экран: клиент поднимает затемнение и ждёт.
  На такие сообщения сервер шлёт 1310 со статусом `none=0`, это только снимает затемнение.

## Инвентарь, магазин, другие базы

- Вещи и деньги лежат в базе `data/af2.sqlite`, отдельно для каждого аккаунта.
- Сумки с 1 — страницы инвентаря (окно рисует только их, сумку 0 клиент не показывает), раскладка по видам в `bags.pageKinds`. Сумка 50 — удаление, 52 — склад.
- C→S 182 (long id, int bag, int cell; bag -1 = любая свободная ячейка), C→S 184 (long, long — обмен) → S→C 181.
- C→S 195 (long пачка, на которую положили, long перетащенная пачка) — объединение пачек одного предмета. Клиент объединяет их сам и ответа не ждёт; сервер повторяет то же (до размера ячейки) и шлёт 181/190.
- C→S 1309 и 1300 (int магазин, string категории) → S→C 1300. Категории — это `wtype`.
- C→S 1310 (int магазин, int шаблон, int количество) → S→C 181, 21 (деньги), 1310 (`ok=...`, `no_money=0`).
- Цена в 1300 — строка `кредиты|эрги|предмет|сколько|…`. Клиент разрешает покупку, только если хватает всех частей сразу, а валюту в 1310 не передаёт. Поэтому вещь стоит либо кредиты, либо, если цены в кредитах нет, эрги из `pricePt` её описания (из клиента). Цена из `shop.prices` всегда в кредитах. За эрги продаются только вещи из списков `config/shops.json`; сейчас в них таких нет.
- Цена уходит строкой `деньги|премиум|предмет`. Каждая база продаёт свой список из `config/shops.json` (по гайду «Что, Где, Почем?»); `shop.guideStock: false` возвращает продажу всего, у чего есть цена.
- C→S 134 (тройки база/локация/точка) → S→C 134 и глобальная карта. C→S 136 — только начало анимации,
  C→S 137 — прибытие, ответ как на 138. Перед переходом на другую базу сервер шлёт её 150.
- Из Убежища на другие базы ведёт дверь «Выход на глобальную карту»: Изумрудное, Плато, Дельта, Пустошь, Карасиный пруд. Список направлений у каждого выхода записан в сцене клиента. Кнопки карты своей базы клиент закрывает по уровню сам.
- Рыба на Пре, озере Изумрудном и на локациях без данных придумана (`INVENTED` и `COPIED` в `tools/gen_fish.py`).

- Рецепты, которые персонаж уже знает навсегда (или знал всегда), в магазине не показываются: клиент сам не помечает известные рецепты. Рецепты с ограниченным числом использований остаются — повторное изучение их добавляет.
- «Магазин пакетов» в клиенте продавал наборы за реальные деньги, на этом сервере его не купить. Вещи из трёх наборов («Быстрый старт», «Волгаръ премиум», «Матч премиум»: удилище, катушка, леска, поплавок или кормушка) продаются в магазине Убежища за кредиты. Цены в кредитах взяты из клиента (`priceCr`), у Матч-Премиума её нет, и она придумана (`shop.prices`). 50 эргов из «Быстрого старта» не продаются.

Деньги, вещи, уровень, опыт, садок и личные рекорды по видам хранятся в

- Рыба попадает в садок, когда игрок оставил её в окне улова (1135/1136). Сообщения
  174 и 175 возвращают садок при входе, 176/177 перекладывают между садками, 286
  выпускает, 285 меняет садки местами.
- Опыт начисляется за рыбу в садке (155). Новый уровень приходит сообщением 103,
  затем 102 обновляет персонажа. Личный рекорд (106) умножает опыт на 3: это
  единственное число из текста клиента, остальные формулы придуманы и лежат в

- Скупщик: разговор с NPC (60) открывает окно продажи (1200), 1205 показывает цены,
  1210 продаёт. Какой NPC на старом сервере скупал рыбу, неизвестно, поэтому пока
  рыбу покупает любой. Цены в разделе `fishMarket`.

## Крафт, улов и сбор

- C→S 1710 (long предмет) учит рецепт → S→C 190 и строка `ok`. C→S 1701 (int станок) и 1700 (разделка) → S→C 1700/1701 со списком рецептов.
- C→S 1702 (int станок, int рецепт) после полосы изготовления → S→C 181/190/173 (потраченное), 21, 1000, 125 и 1702 (int предмет, int количество, bool крит). Отказ — 1703 со строкой `no_ingridients=0`, `no_money=0`, `no_workpoint=0`, `no_inventory=0`, `no_user_recept=0`.
- Вместе с рыбой изредка попадается добыча (126, «Поймано: ...»): что именно, взято из гайда, шансы в разделе `loot` настроек.
- Карточка рыбы (1309) одна на все виды: вид клиент берёт из первого числа `basePar` в описании предмета, и сервер подставляет его туда из своего поля предмета `param` (колонка `items.param`). Карточки разных видов не складываются в одну стопку. Карточка ловится вместе с рыбой своего вида (гайд 844577800), но только для видов, которые просят рецепты коллекций (станок 1000; в рецепте вид — четвёртое число ингредиента). Шанс 2% придуман (`loot.fishCardChancePercent`), каждый венок мастерства вида поднимает его на 5% (`mastery.cardPercent`, из гайдов).
- Премиум-валюта тоже ловится с рыбой (`loot.premiumChancePercent`, `loot.premium`): в оригинале её покупали за деньги, здесь шанс и количество придуманы. Новое значение уходит в 21.
- Точки сбора записаны в сценах клиента (`StreamingAssets/Windows/bases/base_N`, MMOItem). Сервер шлёт их по первому 1005 после смены сцены (161), потом только изменения (162): int точка, int модель `restype_N`, int очки работы, две тройки, строка.
- C→S 1500 (int точка) → S→C 1500 `ok=секунды`, `none=0`, `nowp=0`; C→S 1510 (int точка) после полосы → S→C 181, 1000, 125, 162 и 1510 `ok=0`. Что где растёт, сколько стоит очков работы и что выпадает — `config/gathering.json` (места и цены по гайду «Водоёмы, обитатели, наживки, ресурсы»). Нужный навык (Ремесло, Грибник) и его уровень там же; без него ответ `noproff=0`.
- Точки общие для всех и хранятся в базе (таблица `gather_points`: что лежит и когда пустая точка зарастёт, в секундах Unix), поэтому перезапуск сервера их не обновляет, а время зарастания идёт и пока сервер выключен. Точки, которых в сохранённом нет (первый визит на базу или новая точка в сцене), заполняются по `startFilledPercent`; точки, которых больше нет в сцене, удаляются.
- Переработка (ПКМ → «Переработать»): C→S 290 (long предмет) после двухсекундной полосы → S→C 181/190, 1000 и строка 290: `result=предмет/кол-во,...`, `noresult`, `noworkpoints`, `norefine` или `isend`. После `result` и `noresult` клиент сам запускает полосу снова, поэтому перерабатывается вся пачка по одной штуке. Что получается и с каким шансом, написано в `<refine>` описания предмета («предмет/кол-во/шанс%»); цена 20 ОР за штуку, как в окне клиента. Навык «Рефактор» прибавляет к каждому шансу 5% за уровень (`val` из дерева навыков).

## Навыки

- Дерево навыков (какой поднавык чей, что даёт уровень и сколько он стоит) лежит в ресурсах клиента; `af2-launcher` извлекает его в `data/skills.json`. Очки до следующего уровня: a + b × (c + уровень) из атрибута `tech`, как в неиспользуемой формуле клиента.
- C→S 275 (long предмет) после полосы «Изучить» на курсе (вид 34, навык в первом числе `basePar`). Новый навык: уровень 1, его поднавыки появляются с уровнем 0 → S→C 190, 1408 (навык), 1410 (поднавыки), 1400. Повторный курс даёт очки навыку на изучении (по гайду 300, или 100 поднавыку, если навык уже на 5). Уровень персонажа и `reqPerk` курса проверяются, отказ — 1405 `low_root_level`.
- C→S 1405 (int навык) «Поставить на изучение» → S→C 15 (`teech_perk`) и 1401; отказ — 1405 `no_perk`, `max_level`, `low_root_level` (поднавык не выше навыка). При исчерпанном лимите клиент шлёт -1 и сам пищит.
- 1400/1401: int использовано уровней, int лимит, затем навыки: int, bool изучен, int уровень, int уровень с бонусами вещей, float очки, int очки до следующего. 1408 — то же по одному навыку с сообщением «Изучен навык», 1410 — без сообщения.
- В навык на изучении идёт 10% всего опыта (раздел `skills` настроек). Лимит всех уровней вместе придуман: `limitBase + limitPerLevel × уровень`. Курсы продаются за кредиты по придуманным ценам (`shop.prices`), в клиенте у них только цена в премиум-валюте.
- Уровни навыков складываются с бонусами вещей; сила уровня — `val` из дерева клиента. Сервер применяет: «Параметры» и поднавыки — характеристики; Атлетика — максимум еды, жизни и выносливости, Сталкер — радстойкости и воды; Ремесло — шанс крита при крафте (в пунктах), «Опыт ремесла» — меньше ОР крафта, «Глаз ремесленника» — шанс лута (в процентах от шанса, придумано), «Рефактор» — шансы переработки; Ремесло и Грибник открывают сбор. Клиент сам читает Снасти-А, Удочку-А, Леску-А, Ходока, Спринтера, дальность и точность заброса, а также `reqPerk` вещей (без навыка вещь не надеть).
- Джиги, Воблеры и Блёсны помогают со своими приманками. Какая приманка чья, видно по `subType` описания: 6 — твистеры и WCK (их «Вэки» сами дают Джиги), 7 — воблеры VOB и TopW (их «Асп» даёт Воблеры), 4 и 5 — вертушки VIB и колебалки CRL (Блёсны, «колеблющиеся и вертушки» в описании навыка). Насколько навык помогает, не записано нигде: каждое очко прибавляет 5% к шансу поклёвки на такую приманку (`skills.lureBitePercent`, придумано). «Полевая переработка рыбы» прибавляет свои очки к шансу крита на разделочном столе (станок 3, `skills.fishCuttingStation`), тоже придумано по описанию «+x к шансу получить дополнительные ресурсы». Матч и Механик клиент не читает, в гайдах о них ничего нет; сервер их пока не применяет.

## Холодильник

- Клик по холодильнику в сцене — C→S 166 (int номер объекта: 1 у доктора в Убежище, 0 на базах 3, 4, 6, 7, 8), клиент при этом опускает чёрную шторку. Ответ S→C 166 и 1310, снимающий шторку. В 166: int холодильник, int мест, затем записи рыбы как в садке (175). Слева окно показывает садок в работе, справа — рыбу на льду.
- Кнопки окна шлют C→S 167 (в холодильник) и 168 (обратно в садок): int холодильник, long рыба. Клиент сам переносит рыбу и ответа не ждёт. Если сервер не согласен (холодильник не этой базы, нет места), он заново присылает садок (174, 175).
- Холодильник свой на каждой базе; номер холодильника на сервере — номер базы. Рыба на льду хранится среди рыбы персонажа со списком 100 + база: не видна в садке, не продаётся и не идёт в крафт.
- Мест `fridge.cells` (5, придумано) плюс по одному за каждую карточку «Холод» (1266), использованную на этой базе (гайд 1102257736). Скрипт карточки в клиенте прибавляет 1 к квестовому значению `holod_<база>`; сервер делает то же самое, когда карточку прочитали: клиент читает её, как курс, полосой «Изучить» и шлёт C→S 275 (long предмет), а не 1320. Карточку сервер забирает сам (181 или 190). Квестовые значения персонажа (имя → число) хранятся в таблице `quest_values`.
- Холодильник Убежища — докторский, до биомассы в нём 0 мест (`fridge.doctorBases`); на остальных базах он открыт сразу (придумано).

## Статистика и рекорды

- Вкладка «Статистика» — S→C 1150, по строке на вид до конца: int вид, long выловлено, long общий вес, long личный рекорд, float мастерство (100 — это 100%), int венков 0-3. Считается каждая вытащенная рыба, отпущенная тоже (таблица `catches`). Мастерство и три венка — из гайдов 844577800 и 1102257736, сколько рыбы на каждый венок придумано (`mastery.catches`). Каждый венок умножает вес вида при выборе рыбы на 1 + 3% (`mastery.bitePercent`, из гайдов): вид клюёт чаще, и общий шанс поклёвки чуть растёт. И поднимает шанс карточки этой рыбы на 5%.
- Вкладка «Рекорды» — S→C 40 на запрос с 0: int вид, long владелец, string имя, int граммы, int база, int локация, int наживка (клиент рисует её значок, поэтому это всегда настоящий предмет). В оригинале там были рекорды всего сервера, здесь — свои.
- Рекорды теперь помнят локацию и наживку. Старые рекорды без них показывают локацию «База», а при входе засчитываются в статистику как одна выловленная рыба рекордного веса.

## Репутация

- Вкладка «Репутация» — S→C 30, по строке на фракцию до конца: int фракция, int уровень, int очки внутри уровня. Сколько нужно на уровень, клиент считает сам по своей таблице: с уровня n на n+1 нужно `startA + startB * kfB * n`. Эти числа и число уровней каждой фракции взяты из ресурса `RepFractions` в `resources.assets` и лежат в `reputation.factions`. Сервер хранит очки фракции за все уровни вместе (таблица `reputation`).
- О каждом начислении сервер пишет S→C 307 (int фракция, int, int, int очки — средние два клиент пропускает). Перед первым начислением шлёт 305 (int фракция, «Открыта новая фракция»), а на каждом новом уровне — 306 (int фракция, int уровень).
- Генератор в Убежище — NPC 2, его диалог `2.lng`. Узел 1 показывает, сколько биотоплива (1170) с собой (`[cnt]`), и предлагает сдать всё, 1 или 10 штук. 80 очков Убежища за штуку — из гайда 844577800. Ответ «Сдать единицу фарша» есть в файле, но ни в одном гайде, поэтому не показывается.
- Отпущенная рыба даёт репутацию фракции базы. Засчитывается и рыба из садка, и рыба, отпущенная сразу из окна вылова. Что очков больше за тяжёлую рыбу — из гайдов; сколько именно (1 + 1 за каждый кг) — придумано (`reputation.release`). Какой базе какая фракция — `reputation.baseFactions`.
- Навыки «Вклад» (180 «Поплавок», 190 «Спиннинг», 192 «Донный») за каждую вытащенную рыбу на удилище своего вида дают очки союза. По уровню навыка: 2 очка + 1 за каждые 12 кг, 3 + 1/6 кг, 4 + 1/4 кг, 5 + 1/3 кг, 6 + 1/2,4 кг (гайд 1102257736).
- Каждый уровень репутации базы добавляет на ней +10% опыта за рыбу, +4% к шансу лута, +4% удачи (доля трофеев) и +5% к шансу карточки базы (гайды 844577800 и 1102257736, `reputation.perLevel`).
- Ещё нет: задания с доски (тоже давали репутацию), товары и рецепты, которые требуют репутацию (в данных клиента таких требований нет, их проверял сервер).

## Настройки

- `config/settings.json`: порт, персонаж, шансы клёва, вываживание, базы (уровни, цена перехода), стартовый набор.
  Файл допускает комментарии. Применяется после перезапуска сервера.
- `config/settings.local.json` (необязательный, в git не попадает) кладётся поверх `settings.json`: его ключи
  заменяют те же ключи на любой глубине. Для настроек одной машины, например
  `{ "progression": { "experiencePerFish": 4 } }`.
- `config/fish.json`: виды рыбы и список видов по локациям. Генерируется `tools/gen_fish.py`, можно править руками.
- Другой каталог настроек: `--config <папка>`.
- `travel.enforceLevels` закрывает базы ниже их `minLevel`; `false` открывает все базы сразу.
- VIP: патент покупается в окне VIP (C→S 220, int 0 → S→C 21 с новым балансом эргов, 260 со значком и датой окончания, 220 int 1; при нехватке эргов 220 int -1, «Нехватка средств»). Срок хранится в `characters.vip_until` (секунды Unix), продление добавляет дни к остатку. Колонка `characters.vip` — VIP навсегда, ставится руками. Значок VIP открывает кнопки «Узнать цены» и «Продать всё»; когда срок выходит, клиент убирает его сам. Бонусы из окна VIP в клиенте (`vip` в настройках): продажа рыбы +50% (вторая сумма в «Получено X+Y»), опыт за рыбу +50% (в окне вылова и в 155), шанс лута +10% от самого шанса (придумано, что от шанса), +1 очко опыта навыку на изучении за 2 минуты онлайн. В 155 третье число теперь доля опыта в навыки.
- `attributes` задаёт действие Удачи и Образования, в клиенте их никто не читает.
- `shop.enforceLevels` не даёт купить предмет раньше его уровня.
- `bags` задаёт вкладки сумок, размер склада и цену новых ячеек, `fishing.baitPerCatch` — расход наживки.

## Бэклог

Порядок: репутация, навыки, затем остальное. Перед тем как придумывать правила и числа для пункта, сначала искать их в гайдах игроков и архивах; придуманное выносить в настройки.

- Бонусы VIP, которым пока не к чему относиться: ожидание задания и смена титула -50%, налог на почту -50%.
- Смерть при нулевой жизни: потеря части опыта и улова в садке (слова разработчика из обсуждений Steam), защита костюма от радиации. Пока жизнь не падает ниже `vitals.lowestLife`.
- Подсказки предметов иногда перестают рисоваться (белое пустое окно у всех вещей, раньше работали): что их ломает, не найдено, ошибок в логе клиента нет.
- Репутация: задания с доски объявлений; товары и рецепты, которые её требуют (в данных клиента требований нет, нужен список из гайдов).
- Навыки: Матч («позволяет использовать матчевые удочки», но в данных клиента их ничто не требует) и Механик («+x% к параметрам сборных вещей А класса»: каких именно, не найдено) пока ничего не дают; источник курсов кроме магазина (задания Убежища).
- Холодильник: портится ли рыба на льду и сколько мест было в оригинале без карточек — не найдено.
- Квесты (ответы 70-83 уже работают у доктора, доска 700-710): тексты лежат в клиенте, условия и награды надо придумывать. Значок вопроса над NPC клиент рисует сам по квестовым переменным.
- Крафт: конструктор (1705, 1706, рецепты типа 1), рецепты из мутантов.
- Вкладки карточки: титулы и достижения пока пустые.
- Аукцион и артели: окна пустые, других игроков на сервере нет.
- Холодильник 166, почта 1600.
- Веб-интерфейс сервера на локальном порту: кто в игре, время в игре, персонажи и советник по рыбалке. Советник сам подхватывает персонажа, снасть, наживку, локацию и дно последнего заброса и считает прогноз теми же функциями, что поклёвка (доли видов, вес с учётом снасти, поклёвки против «пустых» подёргиваний, цена и опыт за рыбу). Рейтинг мест и наживок: деньги, опыт, клёв, трофеи или конкретный вид; день, ночь или лучшее время; советы, какую деталь снасти купить. Для этого нужно: названия предметов (`iname`) в `data/items.json` и названия локаций в настройках, хранить последний заброс и дно по локациям, отдавать текущее состояние персонажа без чтения базы.
