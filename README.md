# af2-server

Неофициальный сервер для клиента Atom Fishing 2, написанный на Rust. Официальные
серверы игры выключены 01.08.2023, исходники сервера не публиковались, поэтому
протокол восстановлен по клиенту.

Проект не связан с разработчиками и издателем игры. В репозитории нет кода и ресурсов
игры: описания предметов каждый извлекает из своей купленной копии. Таблица рыбы
`config/fish.json` собрана по архивным гайдам игроков в Steam «Водоёмы, обитатели,
наживки, ресурсы» и «Клевалка от Элиаса».

Сервер рассчитан на нескольких игроков, но играть вместе пока нельзя: игроки не видят
друг друга. **Открывать его в интернет пока рано**, см. раздел «Вход и безопасность».

## Как это работает

Клиент говорит по Photon (TCP, порт 9201, имя приложения `AFCServer`), но всю игровую
логику гонит через **два Photon op-кода** со своим бинарным форматом внутри:

```
op 0:  { 0: msgId, 7: (counter + msgId) ^ -124,       2: counter, 5: payload }
op 1:  { 1: msgId, 4: (counter + msgId) ^ 0x0A937F7F, 2: counter, 3: payload }
сервер -> клиент (event / operation response):  { 1: msgId, 3: payload }
```

`payload` — обычный little-endian `BinaryWriter`; строки это `int16` длина + UTF-8.

Слои в коде:

| Файл | Что делает |
|---|---|
| [src/photon.rs](src/photon.rs) | Кадры Photon по TCP и Protocol16 (big-endian) |
| [src/afc.rs](src/afc.rs) | Конверт AF2, чтение и запись игрового payload |
| [src/server.rs](src/server.rs) | Задача на соединение, журнал неотвеченных сообщений |
| [src/world.rs](src/world.rs) | Общее для всех соединений: настройки, хранилище, кто в игре |
| [src/game/](src/game/) | Правила игры, по файлу на систему |
| [src/storage/](src/storage/) | Типаж `Storage` и его реализация на SQLite |

Каждым персонажем владеет задача его соединения, поэтому игровому коду не нужны
блокировки. Если персонажа открыли со второго соединения, первое закрывается.

## Установка для игрока

Нужна купленная Atom Fishing 2, установленная через Steam.

1. Скачай архив из [Releases](https://github.com/kvirund/af2-server/releases) и распакуй его.
2. Запусти `af2-launcher.exe` и выбери сервер: локальный, из списка или свой адрес.
3. Игра запустится сама. При локальном сервере не закрывай окно лаунчера: сервер
   остановится вместе с игрой.

Устанавливать ничего больше не нужно. При первом запуске лаунчер сам прочитает описания
предметов из установленной игры и сохранит их в `data/items.json`. Эти данные принадлежат
игре, поэтому в репозиторий и архив они не входят.

Чтобы запускать из библиотеки Steam, добавь `af2-launcher.exe` как стороннюю игру.
В параметрах запуска можно указать `--server local`, и меню не появится.

Лаунчер записывает адрес сервера прямо в `Assembly-CSharp.dll` и проверяет его при каждом
запуске, поэтому проверка файлов в Steam ничего не сломает. Вернуть исходный адрес:
`af2-launcher --restore`, показать текущий: `af2-launcher --status`. Список серверов
в меню задаётся в `config/launcher.json`.

## Запуск для разработки

Нужен [Rust](https://rustup.rs/). Лаунчер подготовит клиент и запустит сервер, игру оставит закрытой:

```bash
cargo run --release --bin af2-launcher -- --server local --no-launch
```

После первой подготовки сервер можно запускать отдельно:

```bash
cargo run --release -- --trace trace.log
```

Отдельно запущенный сервер слушает `0.0.0.0:9201` и пишет каждое входящее сообщение;
локальный сервер из лаунчера доступен только с этого компьютера. Прогресс лежит в
`data/af2.sqlite`. Параметры: `--config <папка>`, `--db <файл>`, `--bind <ip>`,
`--port <n>`, `--web-port <n>`, `--trace <файл>`.

## Веб-страницы

Сервер открывает их на своём порту, отдельном от игры, чтобы доступ к ним можно было
ограничить отдельно: `server.webBind` и `server.webPort` в настройках (по умолчанию
http://127.0.0.1:9280/, только с этой машины; порт 0 — без страниц).

### Админские изменения на ходу

GET-ручки только читают. Менять персонажа можно POST-ом `/api/admin/do?character=<id>`
с телом JSON и заголовком `X-Admin-Token`. Токен берётся из переменной окружения
`AF2_ADMIN_TOKEN`, иначе из `server.adminToken`; пока он пуст, ручка отвечает 404 и
ничего не делает. Переменная окружения — основной способ: `config/settings.json` лежит
в репозитории и уезжает в каждый релиз, настоящему токену там не место. Localhost сам по
себе не защита: любая открытая в браузере страница может послать POST на 127.0.0.1,
поэтому токен обязателен.

Что можно (`do` выбирает действие):

```
{"do":"give","template":1180,"count":1}      предмет в сумки
{"do":"experience","amount":64}              опыт, с уровнями
{"do":"reputation","faction":1,"points":40}  репутация
{"do":"money","amount":5000}                 деньги, можно минусом
{"do":"premium","amount":10}                 эрги
{"do":"finish_task","task":409}              засчитать задание с наградой
{"do":"drop_task","task":409}                снять задание без награды
```

Каждое выполняется той же функцией, что и в игре (`inventory::give`,
`character::award_experience`, `board::reward` и так далее), на том самом соединении,
которое играет персонажа, между двумя его сообщениями. Поэтому правила не дублируются,
клиент получает обычные обновления и перезапуск не нужен. Ответ — строка о том, что
вышло: 200 сделано, 422 отказ с причиной (предмет не поместился, задания нет),
409 персонаж не в игре, 403 неверный токен.

**Персонаж должен быть в игре.** Иначе менять некому: сервер держит его в памяти только
на время соединения, и вошедший следом игрок перезаписал бы правку. Ответ 409 называет
тех, кто сейчас играет. Это не «пока не сделано», а граница: правка идёт через игру, а
не мимо неё.

Пример:

```bash
curl -X POST "http://127.0.0.1:9280/api/admin/do?character=1" -H "X-Admin-Token: $AF2_ADMIN_TOKEN" -d '{"do":"give","template":1180,"count":1}'
```

### Страницы

Одна страница с разделами; фильтры (база персонажа, конкретная или все; сейчас, день, ночь или сутки; свои наживки, свои и из магазина базы или все; свои удочки или без предела снасти) общие и запоминаются в браузере. Персонаж — тот, кто в игре, или выбранный. Часы игры и время до смены дня и ночи — в боковой панели.

- «Лучший улов» — где и на что ловить с удочками персонажа: лучшие варианты по деньгам, опыту, клёву и трофеям в час и список мест с наживкой (своя, из магазина с ценой или нет), глубиной, кто клюёт (доли видов полосой) и сколько рыбы сходит; по клику — таблица видов.
- «Наживки» — каталог по видам (наживки, насадки, приманки) с поиском; страница наживки: сколько есть, цена, где продаётся, какая удочка, кто её берёт и где на неё клюёт — на лучшей глубине каждого места, с рыбой, которая берёт только выше дна.
- «Рыбы» — каталог с поиском; страница рыбы: вес, цена за кг, глубина, день и ночь, где живёт, какие наживки берёт (свои и из магазина отмечены), шкала веса с пределом самой крепкой удочки и места с наживками по улову этой рыбы в час.
- «Снасти» — собранные удочки персонажа: детали и их тесты, слабое звено, сколько держит, где с ней больше всего денег.
- «Игроки» — кто в игре (база и локация, время в этот раз и всего, деньги, садок, последние забросы) и все персонажи.

Прогнозы советника сервер считает теми же функциями, что поклёвку (`fishing::odds`, бросок веса, цена, опыт с навыками, репутацией базы и VIP), вместе со сходом рыбы, слишком мелкой для наживки. Снасть: рыба тяжелее 2,5 × самого слабого теста удилища и лески сходит (правило клиента, без прибавки за навык); удочка под наживку — спиннинг для приманок, остальные для прочих, из своих берётся самая крепкая. Глубина: «на дне», на 10 см выше `nearBottomCm` от дна (если на месте есть донная рыба: так она клюёт реже, а доля остальных растёт) и глубины, ниже которых часть рыб места не берёт; показывается лучшая для цели. Дно — из последнего заброса персонажа на локации в этой игре, иначе задаётся на странице (по умолчанию 2 м). В час: запрос поклёвки раз в 5 с плюс время на вываживание и новый заброс (по умолчанию 20 с, меняется на странице). Место выбирается одним списком: «Где персонаж», «Все базы» или база с её локациями — выбрав локацию (например, Лодочную базу), получаешь варианты только для неё, и каталоги наживок и рыб тоже сужаются до неё. Локация называет свою базу, поэтому `location` в запросе перекрывает `base`.

На странице рыбы задаётся целевой размер (`size`: обычная, крупная, трофей). Прогноз считает улов по классам (`byClass` у вида и у всей поклёвки), и выбранный размер становится важнее цели: места сортируются по тому, сколько рыбы именно этого класса берётся в час. Под размер подбирается и снасть (`tackleAdvice`): сколько держать — верх класса (у обычной это вес крупной, у крупной — вес трофея, у трофея — `trophyGrams × topWeightFactor`); какие удочки персонажа это держат и какое звено сдаёт первым; и самые дешёвые удилище, катушка и леска из продающихся на базе, которые дотягивают. Удилище и леска несут клиентский предел (2,5 × теста), катушка считается, только когда `tackleWeightFactor` включён. JSON: `/api/world` (базы, рыбы, наживки, часы) и `/api/advisor` (параметры — в `src/web.rs`).

Страницы читают копию персонажа, которую его соединение обновляет каждые несколько секунд, а не базу, поэтому игре не мешают; персонажей не в игре — из базы. Время в игре копится в квестовом значении `played_seconds` с этой версии. Названия локаций — `locationNames` в настройках (из клиентского `maps.txt`). Только GET, без входа: закрывать доступ — на уровне сети.

## Вход и безопасность

Клиент сам сообщает свой SteamID, и сервер пока ему верит: зная чужой SteamID, можно
войти в чужой аккаунт. Steam-билет клиент не отправляет, поэтому проверить его нельзя.

Клиент умеет показывать окно PIN-кода: сервер отвечает на вход статусом `PIN`, и клиент
повторяет запрос с кодом. Для открытого сервера подойдёт такая схема: сайт подтверждает
SteamID через Steam OpenID и выдаёт PIN, а сервер проверяет его и ограничивает попытки.

Уровни, принадлежность персонажа и предметов сервер проверяет сам.

## Хранилище

Игровой код работает только с типажом `Storage`. Сейчас есть SQLite в режиме WAL: одна
запись за раз, чего хватит на десятки игроков. PostgreSQL понадобится, если сервер
будет работать в нескольких процессах, и потребует ещё одной реализации типажа.

## Подготовка клиента

Всё делает лаунчер. Клиент выбирает адрес одной строкой в `Assembly-CSharp.dll`.
Сборка не подписана, поэтому строку можно заменить на месте: новый адрес не длиннее
исходного (26 символов), а порт в клиенте всегда 9201. Другой способ — запись в файле
`hosts` для `gamesrv1.af2.cryptodev.app`, он пока не проверялся.

> **Про `isLocalServer`.** В клиенте есть дев-переключатель на локальный сервер, и в
> реестре даже лежит `HKCU\Software\R-Age\AFCGame\isLocalServer_h2848998327`. Но
> ставить его **бесполезно**: обфускатор переставил строковые литералы между
> методами-пустышками, и ключ настройки, который реально читается в рантайме, —
> не `isLocalServer`. Проверено: флаг стоит 1, а клиент всё равно идёт на
> прод-адрес. Поэтому патчится именно прод-слот, и флаг больше не нужен.

**Запуск.** Только через Steam (`steam://rungameid/557780`). При прямом запуске
`AFCGame.exe` Steamworks не поднимается (`SteamAPI_Init() failed`), и игра
требует запустить клиент Steam.

**Что можно добыть** — `tools/reachability.py` проверяет, какие предметы игрок может
получить на этом сервере (магазины, стартовый набор, улов, сбор, рецепты с доступными
рецептами и ингредиентами), и для остальных пишет причину. Нужны `data/items.json` и
`data/recipes.json`, которые делает лаунчер:

```bash
python tools/reachability.py "C:/Program Files (x86)/Steam/steamapps/common/AF2" data/reachability.md
```

**Нажатия в окне игры** — `tools/ui.ps1` (скриншот и клик через user32):

```bash
powershell -File tools\ui.ps1 -Action shot -Out shot.png
powershell -File tools\ui.ps1 -Action click -X 968 -Y 545
```

Две грабли, обе стоили времени:

- Скрипт требует, чтобы окно игры было на переднем плане, и восстанавливает его:
  полноэкранное окно Unity само сворачивается при потере фокуса. Без этой проверки
  легко снять скриншот или кликнуть в чужое приложение — один раз так и вышло,
  скриншот поймал другую запущенную игру.
- Клики через `mouse_event` срабатывали не всегда, причина неизвестна. Скрипт
  использует `SendInput` с абсолютными координатами.

**Фокус забирает только `-Action click` и `-Action focus`.** `shot` намеренно этого
не делает и просто откажется снимать, если окно игры не на переднем плане: утащить
окно под руками у человека, который работает за этой же машиной, — худшее, что может
сделать отладочный скрипт.

Для обычной отладки берите `PhotonProbe` — он не трогает ни окно, ни фокус. Игра
нужна только чтобы проверить разбор на стороне клиента.

## Проверка без игры — основной способ отладки

`tests/PhotonProbe` — это **настоящая** библиотека Photon из клиента
(`Photon3Unity3D.dll`), натравленная на наш сервер. Она повторяет весь обмен логина,
поэтому сервер можно крутить **не запуская игру**: ни окна, ни перехвата фокуса,
ни кликов.

```bash
dotnet run --project tests/PhotonProbe/PhotonProbe.csproj -- 127.0.0.1:9201 my-test-account
```

Ожидаемый вывод:

```
[status] Connect
-> msg 90    <- event msg 90, 8 bytes   02 00 4F 6B 01 00 00 00
-> msg 105   <- event msg 105, 28 bytes 50 C3 ... EA 07 0B 00 08 00
-> msg 110   <- event msg 110, 69 bytes ... персонаж ...
             <- event msg 111, 0 bytes
```

Живой клиент нужен только для проверки того, что он сам парсит ответы — как с
blob'ом внешности, падение которого нашлось именно так.

### Живой обмен

```
[c1] connected from 127.0.0.1:60468
[c1] init request, application = "AFCServer"
[c1] <- msg 90 via op1, counter 1, checksum ok, 87 bytes
[c1]    LOGIN REQUEST  marker=1731 login="" password=<empty>
        steamId="<SteamID>" persona="<имя в Steam>" steamLogin=True pin=0
[c1]    -> LOGIN OK (account 1)
[c1] <- msg 255 ...   <- ровно те три сообщения, которые
[c1] <- msg 105 ...      клиент шлёт после успешного логина
[c1] <- msg 110 ...
```

`msg 255` с нулевым int приходит и дальше каждые 10 секунд — это heartbeat.

### Что известно про сообщения

| id | Направление | Содержимое |
|---|---|---|
| 90 | клиент → сервер | `Int64 marker` (1731), login, password, steamId, deviceId, persona, `Bool` steamLogin, `Int32` pin |
| 90 | сервер → клиент | `String` статус (`"Ok"` или `"PIN"`); при `Ok`: `Int32` id аккаунта, `String` токен привязки, `Int32` флаг |
| 255 | клиент → сервер | heartbeat, `Int32 0`, раз в 10 с |
| 105 | клиент → сервер | запрос валюты; ответ — два `Int64` |
| 110 | клиент → сервер | запрос списка персонажей |
| 110 | сервер → клиент | записи подряд до конца payload: `Int64` id, `String` имя, `Int32` уровень, `Int32` костюм, `Int32` baseId, `Int32` locId, `Int64`, `Int32` длина + blob внешности |
| 111 | сервер → клиент | пустой payload; клиент делает `SceneManager.LoadScene(1)` → экран выбора персонажа |
| 87 | клиент → сервер | строка со steamId — кнопка «Привязать аккаунт к Steam» |
| 1005 | клиент → сервер | 96 байт из `Fisherman.cs` — состояние и позиция игрока, раз в ~3 с |
| 60 | клиент → сервер | 16 байт из `ActiveObject.cs` — взаимодействие с объектом на базе (NPC) |
| 100 | клиент → сервер | `Int64` id персонажа — кнопка «В игру» (`SelectShadowLogic.goToGame`) |

Список берётся из `globalgamemanagers`, а не из догадок — я один раз предположил,

**Токен привязки в ответе на логин обязателен.** Формально это поле необязательное —
клиент читает его только если в payload ещё остались байты. Но если его не прислать,
`JBEHMPDDMME.AMJCBLPKNCB` остаётся пустым, и `SelectShadowLogic.checkPriv()` решает,
что аккаунт не привязан к Steam:

```csharp
if (AMJCBLPKNCB == "") { steamConnectBtn.SetActive(true);  toGameKey.SetActive(false); }
else                   { toGameKey.SetActive(true);        steamConnectBtn.SetActive(false); }
```

То есть кнопка «В игру» просто не появляется, вместо неё висит «Привязать аккаунт
к Steam», и из экрана выбора персонажа выхода нет. Сервер отдаёт в токене тот
steamId, который клиент прислал в логине.

Полезно на будущее: `checkPriv` размножен обфускатором в 15 клонов с переставленными
`true`/`false`. Настоящий — тот, которому оставили читаемое имя; остальные мусор.

**Одного 151 мало.** Сцена Base загрузится, но будет каждый кадр падать в
`LocNewLogic.Update()` и `Fisherman.Update()` — чёрный экран. 151 только грузит
сцену, а текущую базу выставляют данные локаций. Порядок обязателен:

```
145  каталог баз          -> заполняет словарь
150  детали базы          -> индексируется в этот словарь, иначе KeyNotFound
151  загрузить сцену
```

`EDLNGHBMJBL.AADJMFJMAGF` ищет локацию по паре (baseId, locId) персонажа. У нашего
персонажа locId = 0, поэтому **локация с id 0 должна быть в сообщении 150** —
иначе поиск вернёт null и начнутся те же NRE.

Детали базы (`LKDIADGGOLN.CPKLGCKGHFN`): `Bool`, 3×`Int32`, `Bool`, `DateTime`
(6×`Int16`), `Int32` число локаций, и на каждую — `Int32` baseId, `Int32` locId,
затем `Int32`, `Int32` mapX, `Int32` mapY, `Bool`, `Bool`, `Int32`, `Int32`.

Базы лежат в `StreamingAssets/Windows/bases/base_N`, так что id базы должен быть
из реально существующих (1..9).

**Blob внешности** (`Character.initShadowsParams`) — плоский набор байт, каждый индекс
в палитре `Customizator`. Первые 17 читаются безусловно, более короткий blob роняет
экран выбора персонажа через `EndOfStreamException`:

```
[0]      1 = мужчина, иначе женщина
[1]      цвет волос
[2..3]   цвет верха, цвет низа
[4..5]   камуфляж верха, камуфляж низа
[6..9]   верх:  intensive, scale, rotate, hue
[10..13] низ:   intensive, scale, rotate, hue
[14..16] читаются и выбрасываются
дальше опционально: борода, усы (bool)
```

## Что уже есть из игровых данных

  Всё это лаунчер кладёт в `data/items.json`. `modelid` и `imageid` пусты у всех, их не берём.
- Чего в описаниях нет, хотя место отведено: второе число `basePar` — размерный класс только

- Локализация и структура: `ItemsData.xml`, `WpnLang.xml`, `Perks.xml`, `QTask.xml`,

## Рыбалка

- C→S 1120 раз в 5 с, пока наживка в воде. Ответ S→C 1120: `false + float` или поклёвка
  (формат в `src/game/fishing.rs`). Вываживает клиент сам.
- C→S 1130 (индекс удочки) → S→C 1130 с рыбой. C→S 1135/1136 (id рыбы) → S→C 1135 с опытом.
- `config/fish.json` собирает `tools/gen_fish.py` из архивных копий гайдов игроков в Steam:
  виды по локациям, пороги «маленькая / крупная / трофей», наживки, правила глубины и ночи.
  Шанс клёва, доли видов и размерных классов, верхний вес (1,5 трофейного), параметры
  вываживания и опыт нигде не записаны и заданы в `config/settings.json`.
- Привлекательность наживки, насадки или блесны (первое число `basePar`, норма 100) умножает шанс поклёвки, и сонар показывает уже его. Что она влияет на клёв, сказано в описании предметов клиента; сам множитель придуман (`fishing.baitAttraction`, 0 выключает).
- Размер наживки — второе число `basePar`, округлённое: класс 0 это мотыль и муха,
  1 хлеб и опарыш, 2 жук и живец, 3 выползок, лягушка и пучок червей. Правило целиком
  клиентское, читается в `Fisherman.klevAction` (`Assembly-CSharp.dll`): этим числом
  клиент лезет в свою таблицу весов — класс 0 это 0–500 г, 1 — 500–3000, 2 — 3000–7000,
  3 — 7000–20000, 4 — 20000–200000 — и берёт нижнюю границу как самую мелкую рыбу,
  которая держится на наживке. Рыбу легче он сбрасывает с вероятностью
  `(минимум − вес) × (1 + shy / 100) / (вес + 0,1) × 20` процентов, где shy — пятое поле
  ответа 1120 (сервер пишет туда 0). На классе 1 это значит: всё легче ~85 г сходит
  всегда, 142 г сходит в половине поклёвок, 380 г — в 6%. `BAIT_MIN_GRAMS` и
  `DROP_PERCENT` в `fishing.rs` — это та же таблица и то же число, не придуманные.
  Класс из таблицы есть только у живых наживок: у блесны второе число — её собственный
  размер (8, 15, 25…), у имитаций и бойлов — метка (49, 1010), и `case` под них в клиенте
  нет. То, что мы считаем у них порог нулевым, тоже не догадка: клиент собирает ответ как
  `(0, 10000, 0)` до `switch` и для незнакомого числа возвращает его как есть, а сравнивает
  потом с первым полем. Сход клиент проверяет не на всякой снасти: ветка спиннинга берёт
  рыбу независимо от броска. На игру это не влияет — на спиннинг идёт только блесна,
  а у блесны порога и так нет.
- Сход целиком на клиенте: при сходе он дёргает поплавок на 0,15 с и сигнал не включает
  (сигнал бывает только когда рыба не сошла, и только если у поплавка есть
  `signal_enable`). Поэтому сигнальный поплавок про мелочь молчит по устройству. Сервер
  то же правило не применяет: когда он считал его ещё раз, карась в 142 г на хлебе
  доходил до сигнала в четверти случаев вместо половины. `drop_chance` остался только
  советнику, чтобы прогноз учитывал то, что сделает клиент.
- `fishing::bait_from_class` отвечает, **с какого размерного класса** наживка держит
  рыбу вида: 0 — обычную и выше, 1 — с крупной, 2 — только трофейную, 3 — никакую,
  то есть на неё этот вид не ловится. Одного числа хватает, потому что правило отпускает
  рыбу только за малый вес: раз класс держится, все, кто тяжелее, держатся тем более.
  Класс берётся по середине его весовой полосы: по нижней границе любая наживка
  выглядела бы хуже, чем играет. Из 626 пар 494 без пометки, 58 с «от крупной»,
  19 с «только трофей» и 55 скрыты совсем; ни один вид не остаётся без наживки.
  Голавль бежит 132–924 обычный, 924–3357 крупный, 3357–5036 трофей, и при пороге жука
  в 3000 г жук у него «от крупной»; уклейка растёт до 218 г при пороге хлеба в 500 —
  у неё хлеб «только трофей», а у малька, который до 43 г, хлеб скрыт.
- `fishing::bait_fits` строже и отвечает на другой вопрос: держится ли на наживке
  **обычная** рыба вида. По ней доска выбирает наживку для задания, потому что задание
  просит рядовую рыбу и помногу. Для страницы рыбы это правило не годится — так ловят
  трофеи, и прятать такие наживки значит прятать сам способ.
- Что снасть не держит, решает клиент. Через 2 с после подсечки рыба тяжелее
  min(тест удилища, тест лески) × (2,5 + 0,04 × навык) кг уходит со словами «Слишком большая рыба».
  Фрикцион клиент сам ставит на 80% самой слабой части снасти: тяжёлая рыба на нём тянет леску,
  пока не выберет её всю, или сходит сама (шанс в секунду — пятое число после выносливости в 1120).
  Леска рвётся или удилище ломается, только когда игрок затянет фрикцион и нагрузка дойдёт до 99%.
  Ни о сходе, ни о «всей леске» клиент серверу не пишет. `fishing.tackleWeightFactor` больше 0
  возвращает прежний потолок: рыба не тяжелее самого слабого теста × это число.
- Поломки в бою: C→S 1305 (long предмет) — сломалось удилище или порвалась леска до 10 м целиком;
  1306 (long леска, float метры) — оторвался кусок лески (1–4 м); 1307 (long предмет) — по разу
  на каждую ушедшую с леской вещь: крючок, наживка, поплавок, блесна, кормушка. 910 — новость
  для других игроков. Клиент откладывает сломанное у себя в сумку 500 и длину лески у себя
  не меняет, поэтому сервер удаляет вещи (190), забирает по одной штуке ушедших (181/190),
  а остаток лески хранит в `param` предмета и подставляет третьим числом `basePar` (181).
- Номер локации приходит только в C→S 138, поэтому сервер запоминает его для 1120.
- Поле размера в 1120 — доля 0..1 между мин. и макс. моделью; поле качества в 1130 — класс 0..2.
- Игровое время клиент считает по часам ПК; 12 игровых часов за реальный взят из гайда.
- Вес крючка входит в скорость погружения: у крючка «Гладь-20-0» он равен -8, снасть
  с ним всплывает и поплавок лежит.
- Запрос без ответа может оставить чёрный экран: клиент поднимает затемнение и ждёт.
  На такие сообщения сервер шлёт 1310 со статусом `none=0`, это только снимает затемнение.

## Инвентарь, магазин, другие базы

- Вещи и деньги лежат в базе `data/af2.sqlite`, отдельно для каждого аккаунта.
- Сумки с 1 — страницы инвентаря (окно рисует только их, сумку 0 клиент не показывает), раскладка по видам в `bags.pageKinds` (жетоны — «Валюта», карточки и открытки — «Коллекции», остальное без своей вкладки — «Разное»). Вещи, которые лежат в «Разном», хотя у их вида теперь есть своя вкладка, при входе переезжают туда, если там есть место. Сумка 50 — удаление, 52 — склад.
- Расширение: C→S 210 (int сумка) → S→C 210 (int сумка, две строки `деньги|эрги|предмет|сколько` — два способа оплаты). C→S 215 (int сумка, int способ) → S→C 181/190 (потраченные жетоны), 21, 102, 215. Первый способ — жетоны: трофейщика (1179) для сумок (гайд 844577800: «жетоны трофейщика … или за реалы»), кладовщика (1336) для склада (гайд 1102257736); второй — эрги. Сколько жетонов и ячеек — придумано (`bags`), каждая следующая покупка в той же сумке дороже на шаг.
- C→S 182 (long id, int bag, int cell; bag -1 = любая свободная ячейка), C→S 184 (long, long — обмен) → S→C 181.
- C→S 190 (long предмет) — предмет выброшен в корзину после вопроса «вы уверены». Клиент убирает его у себя сам; сервер удаляет предмет целиком (всю пачку) и повторяет 190, а для надетого ещё шлёт 102 и навыки. Другие формы 190 (с холодильником или местом перед предметом) этим не считаются.
- C→S 195 (long пачка, на которую положили, long перетащенная пачка) — объединение пачек одного предмета. Клиент объединяет их сам и ответа не ждёт; сервер повторяет то же (до размера ячейки) и шлёт 181/190.
- C→S 1309 и 1300 (int магазин, string категории) → S→C 1300. Категории — это `wtype`.
- C→S 1310 (int магазин, int шаблон, int количество) → S→C 181, 21 (деньги), 1310 (`ok=...`, `no_money=0`).
- Цена в 1300 — строка `кредиты|эрги|предмет|сколько|…`. Клиент разрешает покупку, только если хватает всех частей сразу, а валюту в 1310 не передаёт. Поэтому вещь стоит либо кредиты, либо, если цены в кредитах нет, эрги из `pricePt` её описания (из клиента). Цена из `shop.prices` всегда в кредитах. Гайд, из которого собраны списки `config/shops.json`, перечисляет только товары за кредиты, поэтому вещи с ценой в одних эргах (128 штук: наживки, бойлы, блёсны, аптечки, сырьё для ремесла, рецепты, VIP, поездки, ящики, стулья) продаются на всех базах сверх списков — `shop.premiumEverywhere`. Где они стояли в оригинале, неизвестно, это придумано; с `false` они не продаются нигде.
- Вторая часть цены — предметы (`costWpn=` в клиентской таблице, поле `cost_item` в `data/items.json`): чаще всего жетоны трофейщика (ЛакЛайн, Рубикон, курсы союзов), иногда жетоны исследователя или рекордсмена, турнирные жетоны, блёсны (Рима, Круциан). Сервер шлёт её как `предмет/штук` (клиент читает `/` как `|`) и при покупке забирает вместе с деньгами, как в гайде 1387968453 («ЛакЛайн-7 210,00 + Жетон Трофейщика x60»); не хватает — `no_money=0`. Вещи, которые гайд продаёт только за деньги (рецепты червей, кусочков рыбы и потрохов, лески Плимус), перечислены в `shop.noItemPrice`.
- Цена уходит строкой `деньги|премиум|предмет`. Каждая база продаёт свой список из `config/shops.json` (по гайду «Что, Где, Почем?»); `shop.guideStock: false` возвращает продажу всего, у чего есть цена.
- C→S 134 (тройки база/локация/точка) → S→C 134 и глобальная карта. C→S 136 — только начало анимации,
  C→S 137 — прибытие, ответ как на 138. Перед переходом на другую базу сервер шлёт её 150.
- Из Убежища на другие базы ведёт дверь «Выход на глобальную карту»: Изумрудное, Плато, Дельта, Пустошь, Карасиный пруд. Список направлений у каждого выхода записан в сцене клиента. Кнопки карты своей базы клиент закрывает по уровню сам.
- На какой базе персонаж — `travel::current_base`: по локации, если она чья-то; иначе та, куда он последний раз пришёл (`player.base`); иначе стартовая. Порядок важен: стоя на самой базе локация равна нулю и не называет базу, так что знает её только персонаж. Кнопка «на базу» раньше спрашивала только локацию и скатывалась к стартовой базе — с любой базы, кроме Убежища, она уносила в Убежище.
- Рыба на Пре, озере Изумрудном и на локациях без данных придумана (`INVENTED` и `COPIED` в `tools/gen_fish.py`).
- Два гайда расходятся в том, где какая рыба стоит. Списки по локациям берутся из «Водоёмы, обитатели, наживки, ресурсы»; где второй гайд, «Клевалка от Элиаса», явно называет ту же воду и держит рыбу, которой в первом нет, он добивает список (`FROM_CHART` в `tools/gen_fish.py`). Пока там один голец: Элиас ставит его на пять точек Убежища — Протока, Серебронкс, Затон, Мост, Склон, — а списки по локациям знают только Протоку.

- Рецепты, которые персонаж уже знает навсегда (или знал всегда), в магазине не показываются: клиент сам не помечает известные рецепты. Рецепты с ограниченным числом использований остаются — повторное изучение их добавляет.
- «Магазин пакетов» в клиенте продавал наборы за реальные деньги, на этом сервере его не купить. Вещи из трёх наборов («Быстрый старт», «Волгаръ премиум», «Матч премиум»: удилище, катушка, леска, поплавок или кормушка) продаются в магазине Убежища за кредиты. Цены в кредитах взяты из клиента (`priceCr`), у Матч-Премиума её нет, и она придумана (`shop.prices`). 50 эргов из «Быстрого старта» не продаются.

## Крафт, улов и сбор

- C→S 1710 (long предмет) учит рецепт → S→C 190 и строка `ok`. C→S 1701 (int станок) и 1700 (разделка) → S→C 1700/1701 со списком рецептов.
- C→S 1702 (int станок, int рецепт) после полосы изготовления → S→C 181/190/173 (потраченное), 21, 1000, 125 и 1702 (int предмет, int количество, bool крит). Отказ — 1703 со строкой `no_ingridients=0`, `no_money=0`, `no_workpoint=0`, `no_inventory=0`, `no_user_recept=0`.
- Рыба по весу (`kgcount` рецепта: «наименьший вес / граммов на штуку»; разделка, филе, мутофарш, копчёный угорь): рыба не легче первого числа даёт штуку на каждые столько граммов, но не меньше обычного количества рецепта. В клиенте об этом только комментарий в XML («количество результата от веса ингредиентов»), как именно считалось — придумано.
- «Конструирование» (рецепты типа 1, все на станке 4, верстак): идут в тот же список 1701 своей записью (`CLFFOBKFKDN.OAKCFGOLKLA`): после стоимости и времени — int «сколько деталей сверх минимума всего», компоненты A–D (деталь / наименьшее число / прибавка за деталь сверх), «исходный предмет» (то, на чём собирают; уходит в сборку), float шанс качества и его модификатор. C→S 1705 (int станок, int рецепт, int добавлено A, B, C, int модификаторов, long исходный предмет, 0 — любой) → то же, что 1702, и S→C 1705 (int предмет, int 1, bool крит). Модификаторы во всех рецептах закомментированы, крита нет. S→C 1706 («Сборка», окно без кнопок) клиент ни на что не открывает — не шлётся.
- Собранная вещь помнит свои детали (колонка `items.parts`: сверх A/B/C и «Механик» сборщика), а сервер переписывает её описание в 180/181: каждая лишняя деталь прибавляет прибавку своего компонента к 1-му, 2-му или 3-му числу `basePar` (так в комментариях рецептов), требуемый уровень растёт на 0,3 и вес на 10% за деталь (как в предпросмотре клиента). Тест удилища, катушки и лески для клёва берётся из этого же описания. «Механик» (150, «+x% к параметрам сборных вещей А класса») прибавляет свои проценты к изменённым числам вещей класса А (`category` 1) — клиент этот навык нигде не применяет, так что как именно — придумано. Такие вещи не складываются в стопку с обычными.
- Лаунчер: `--extract` только извлекает данные игры в `data/` (предметы, рецепты, навыки), ничего не запуская.
- Вместе с рыбой изредка попадается добыча (126, «Поймано: ...»): что именно, взято из гайда, шансы в разделе `loot` настроек.
- Карточка рыбы (1309) одна на все виды: вид клиент берёт из первого числа `basePar` в описании предмета, и сервер подставляет его туда из своего поля предмета `param` (колонка `items.param`). Карточки разных видов не складываются в одну стопку. Карточка ловится вместе с рыбой своего вида (гайд 844577800), но только для видов, которые просят рецепты коллекций (станок 1000 — вкладка «Коллекции» в окне персонажа; в рецепте вид — четвёртое число ингредиента). Шанс 2% придуман (`loot.fishCardChancePercent`), каждый венок мастерства вида поднимает его на 5% (`mastery.cardPercent`, из гайдов).
- Красная икра (наживка 1387): разделка (рецепт 322) берёт рыбу с признаком 108 «Красная икра» — шестое число ингредиента рыбы. Признаки отдельной рыбы (`type_100`..`type_108` в fishLang.txt) идут в записи рыбы первой строкой, числа через запятую, и хранятся в колонке `fish.traits`; вторая строка (видовые типы, `type_1`..`type_31`) пустая, рецепты её не просят. Икру бросает сервер при поимке: лососевые тяжелее 3 кг (гайд 1102257736), шанс 30% придуман (`fishing.traits`). Сам рецепт «Наживка икра» (1388) собирается на станке коллекций из карточек «Озеро» (карточка базы), «Водоросли» (награда заданий «Ресурсы» на досках Озера Кулгу и Оз. Изумрудного, `board.baseResourceItems`, с форума), «Форель» (с любой форели, анонс в Steam, шанс 3% придуман, `loot.speciesCards`) и 10 жетонов трофейщика (терминал С.П.А.С.). Карточка «Рыбалка» по описанию в клиенте ловится на любой базе с любой рыбой (там же, пустой список видов, шанс 1% придуман).
- Премиум-валюта тоже ловится с рыбой (`loot.premiumChancePercent`, `loot.premium`): в оригинале её покупали за деньги, здесь шанс и количество придуманы. Новое значение уходит в 21. Основной же её источник — доска заданий (см. «Доска заданий»).
- Карточка базы падает с рыбы на своей базе (`loot.baseCards`, шанс 1% придуман, репутация базы его поднимает) и попадается в мусоре (по гайду 922250351, в разделе о Пустоши): строка `"baseCard": true` в `config/gathering.json` даёт карточку той базы, где собирают; вес придуман. На Плато великанов и Реке Пра карточек баз в клиенте нет.
- Точки сбора записаны в сценах клиента (`StreamingAssets/Windows/bases/base_N`, MMOItem). Сервер шлёт их по первому 1005 после смены сцены (161), потом только изменения (162): int точка, int модель `restype_N`, int очки работы, две тройки, строка.
- C→S 1500 (int точка) → S→C 1500 `ok=секунды`, `none=0`, `nowp=0`; C→S 1510 (int точка) после полосы → S→C 181, 1000, 125, 162 и 1510 `ok=0`. Что где растёт, сколько стоит очков работы и что выпадает — `config/gathering.json` (места и цены по гайду «Водоёмы, обитатели, наживки, ресурсы»). Нужный навык (Ремесло, Грибник) и его уровень там же; без него ответ `noproff=0`.
- Точки общие для всех и хранятся в базе (таблица `gather_points`: что лежит и когда пустая точка зарастёт, в секундах Unix), поэтому перезапуск сервера их не обновляет, а время зарастания идёт и пока сервер выключен. Точки, которых в сохранённом нет (первый визит на базу или новая точка в сцене), заполняются по `startFilledPercent`; точки, которых больше нет в сцене, удаляются.
- Переработка (ПКМ → «Переработать»): C→S 290 (long предмет) после двухсекундной полосы → S→C 181/190, 1000 и строка 290: `result=предмет/кол-во,...`, `noresult=1`, `noworkpoints=1`, `norefine=1` или `isend=1`. Клиент делит строку по `=` и берёт ключ до него; без `=` ключ у него «-», поэтому голое `isend` он не узнаёт. После `result` и `noresult` клиент сам запускает полосу снова, поэтому перерабатывается вся пачка по одной штуке. Что получается и с каким шансом, написано в строке `refine=` клиентской таблицы предметов («предмет/кол-во/шанс%»; лаунчер кладёт её в поле `refine` в `data/items.json`). По ней же рисует окно клиент; `<refine>` внутри описания предмета старее и расходится с ней: у карточек (дают «Старую карту»), курсов («Страницу») и нескольких других; цена 20 ОР за штуку, как в окне клиента. Навык «Рефактор» прибавляет к каждому шансу 5% за уровень (`val` из дерева навыков).

## Упаковки и ящики

- Вещи с пунктом «Использовать» (wtype 30, и жетоны wtype 27) клиент открывает той же полосой и тем же C→S 275 (long предмет), что и курсы. Что каждая делает, записано в её же скрипте на Lua (`<useScript>` в таблице предметов клиента): оригинальный сервер выполнял его. Сервер разбирает эти скрипты (`scripts.rs`) и выполняет вызовы: `giveWeaponToUser` — выдать вещи; `rndChanceList` — одна вещь из списка «предмет/от/до/вес» по весу, количество от-до; для «Карточки в упаковке» карта рыбы получает вид из списка в скрипте (`rndlist`); `teachRecept` — рецепт с числом применений (-1 — навсегда); `addExp`, `addVIPStatus`, `addWorkPoints`, `addReal` — опыт, VIP, ОР, эрги из `basePar` предмета; `addActiveEffectLUA` — эффект на время; `gu.nav_point` — импланты; `resetParametrs`; `goToLoc` — поездки; `setQValue("holod_"..база)` — то же, что карточка «Холод». Нет вызова — вещь ничего не делает (Припасы, Разделки, Значок «Меценат», жетоны улучшения).
- Что веса в списке — доли, а не проценты с шансом пустого ящика, — догадка: в «Карточке в упаковке» нет проверки на пустой результат.
- Вещи сначала проверяются на место в рюкзаке; не помещаются — предмет остаётся. Потом он тратится (181/190), вещи приходят (181), а выпавшую из списка клиент показывает окном «получено» (S→C 1704, long предмет, как в скрипте). Итог — строка в системную вкладку чата.
- Эффекты (`effects.rs`): 21 «Обучение +X%» — больше опыта за рыбу, хранится в квестовых значениях персонажа (конец и сила), значок — S→C 260 с иконкой 21 и X в подсказке, при входе приходит снова. Повторное использование не суммируется: остаётся дальний конец и большая сила («эффекты не суммируются» в описании жетона рекордсмена). Эффект 20 — VIP на время. Жетон рекордсмена даёт оба на 4 часа, карточка «Обучение +50%» — на 2 часа, экстракт опыта 100 — ещё 5 минут обучения.
- Импланты I-III прибавляют 1-3 к пределу уровней навыков (`nav_point`, в описании «свободное очко параметров»: параметры здесь — навыки ветки «Параметры»). «Сброс параметров» ставит «Параметры» на 1, его поднавыки на 0 и освобождает эти уровни под пределом.
- Поездки переносят на свою локацию (S→C 150, 158, 160; на Убежище — 150 и 151). Ограничение «на 4 часа» у поездки на Оз. Изумрудное не держится: эта база на сервере и так открыта.
- Турнирный жетон по своему скрипту добавляет место в холодильник базы, как карточка «Холод» (в клиенте у него скрипт этой карточки).

## Доска заданий

- C→S 700 (int вкладка) — клик по доске и переключение вкладок: 1000 «Доход», 1010 «Ресурсы», 1020 «Опыт и реп.», 1100 «Ежедневные», 1110 «Турниры». S→C 710 — одна строка: `ok=1` (окно закрывается), `no_task` (клиент сам запросит доску снова), `no_repa`, `no_get`, `big_count` («уже взяли задание этого типа» — здесь это то же предложение), `no_time_period` («не чаще, чем один раз в 40 минут» — здесь только у ежедневных). S→C 670 (int команда, long id до конца): 1 убрать вкладку, 2 убрать задание, 3 взято, 4 выполнено, 5 продвинулось. S→C 672 (long рыба) — рыба забрана заданием из садка («принята по квесту»).
- Тексты заданий (`QTask.xml`): 1 — N рыб, 2 — N рыб от веса, 4 — N трофеев, 5 — общий вес рыб от веса, 6 — общий вес, 7 — общий вес на наживку. Засчитывается рыба, пойманная на базе, где взято задание (гайд 1102257736), положенная в садок кнопкой «в садок» (1135), а не «Без квеста» (1136); рекордная — нет (обновление 139: «Рекордная рыба больше не принимается в квесты автоматически»): доска забирает засчитанную рыбу. Задания NPC рыбу не забирают, поэтому в них идёт и рекордная — иначе у нового персонажа, у которого рекорд почти каждая первая рыба вида, первые уловы не засчитываются (по-нашему). Одна рыба идёт в одно задание доски — первое взятое из подходящих (по-нашему: сданная рыба уходит, и как выбирал оригинал, не записано); кроме ежедневных, задание её забирает (обновление 147.1: «в ежедневных рыба не удаляется»). Задания NPC рыбу не забирают, и в них одна рыба засчитывается во все подходящие строки. Выполненное задание сразу даёт награду, о ней пишется строка в системную вкладку чата.
- Предложения общие для всех игроков, живут, пока работает сервер, и меняются целиком раз в `board.refreshMinutes` (ежедневные — `dailyRefreshMinutes`, к этому же сроку их надо выполнить). Вид — из рыбы локаций базы с учётом её доли, цвет — по `qualityWeights`; цвет увеличивает размер задания и награду, ресурсов за него даётся цвет + 1 (по форуму: чёрный 1 … золотой 5). «Доход» платит `incomePercent` от цены рыбы у скупщика, «Опыт и реп.» — опыт рыбы × `experiencePercent` и репутацию базы, «Ресурсы» — предмет из `resourceItems`, ежедневные — деньги и опыт. Эрги в оригинале давала доска, и здесь тоже: `experienceReals` на «Опыте и реп.» и `incomeReals` поменьше на «Доходе», от и до, с той же надбавкой за цвет. 4–8 эргов за задание «опыта и реп.» — с форума разработчиков (2016: «квест с дружелюбной репутацией имеет 4,19 эрга», «с репутацией Уважение бывают квесты до 7-8 эргов»), про «доход» там же: «эрг, припасы». `[0, 0]` — не давать вовсе. Что предложения случайные, у них есть копии и таймер, берут по 3 задания — с форума af-2.ru; сами числа придуманы.

## Навыки

- Дерево навыков (какой поднавык чей, что даёт уровень и сколько он стоит) лежит в ресурсах клиента; `af2-launcher` извлекает его в `data/skills.json`. Очки до следующего уровня: a + b × (c + уровень) из атрибута `tech`, как в неиспользуемой формуле клиента.
- C→S 275 (long предмет) после полосы «Изучить» на курсе (вид 34, навык в первом числе `basePar`). Новый навык: уровень 1, его поднавыки появляются с уровнем 0 → S→C 190, 1408 (навык), 1410 (поднавыки), 1400. Повторный курс даёт очки навыку на изучении (по гайду 300, или 100 поднавыку, если навык уже на 5). Уровень персонажа и `reqPerk` курса проверяются, отказ — 1405 `low_root_level`. Новый навык клиент объявляет сам (по 1408); об очках с повторного курса и о курсе, который ничего не дал, сервер пишет строкой в системную вкладку чата.
- C→S 1405 (int навык) «Поставить на изучение» → S→C 15 (`teech_perk`) и 1401; отказ — 1405 `no_perk`, `max_level`, `low_root_level` (поднавык не выше навыка). При исчерпанном лимите клиент шлёт -1 и сам пищит.
- 1400/1401: int использовано уровней, int лимит, затем навыки: int, bool изучен, int уровень, int уровень с бонусами вещей, float очки, int очки до следующего. 1408 — то же по одному навыку с сообщением «Изучен навык», 1410 — без сообщения.
- В навык на изучении идёт 10% всего опыта (раздел `skills` настроек). Лимит всех уровней вместе придуман: `limitBase + limitPerLevel × уровень`. Курсы продаются за кредиты по придуманным ценам (`shop.prices`), в клиенте у них только цена в премиум-валюте.

Сервер при загрузке переписывает навык в их описании по названию (`skills.courseSkills`: 410, 415, 425; придумано), и клиент получает уже исправленное. В гайдах этих курсов нет; продаются в Убежище по цене клиента: 50 000 кредитов и 50 жетонов трофейщика.
- Уровни навыков складываются с бонусами вещей; сила уровня — `val` из дерева клиента. Сервер применяет: «Параметры» и поднавыки — характеристики; Атлетика — максимум еды, жизни и выносливости, Сталкер — радстойкости и воды; Ремесло — шанс крита при крафте (в пунктах), «Опыт ремесла» — меньше ОР крафта, «Глаз ремесленника» — шанс лута (в процентах от шанса, придумано), «Рефактор» — шансы переработки; Ремесло и Грибник открывают сбор. Клиент сам читает Снасти-А, Удочку-А, Леску-А, Ходока, Спринтера, дальность и точность заброса, а также `reqPerk` вещей (без навыка вещь не надеть).
- Джиги, Воблеры и Блёсны помогают со своими приманками. Какая приманка чья, видно по `subType` описания: 6 — твистеры и WCK (их «Вэки» сами дают Джиги), 7 — воблеры VOB и TopW (их «Асп» даёт Воблеры), 4 и 5 — вертушки VIB и колебалки CRL (Блёсны, «колеблющиеся и вертушки» в описании навыка). Насколько навык помогает, не записано нигде: каждое очко прибавляет 5% к шансу поклёвки на такую приманку (`skills.lureBitePercent`, придумано). «Полевая переработка рыбы» прибавляет свои очки к шансу крита на разделочном столе (станок 3, `skills.fishCuttingStation`), тоже придумано по описанию «+x к шансу получить дополнительные ресурсы». Матч и Механик клиент не читает, в гайдах о них ничего нет. «Механик» сервер применяет в конструкторе (см. «Конструирование»). Без «Матча» (195) на удочку, где стоит хоть одна матчевая снасть (`fishing.matchItems`: Матч-Премиум, Матч Ролл Премиум, Матч-Лайн, поплавок «Матчевый»), не клюёт, а в системную вкладку чата раз в минуту пишется, что нужен навык; как именно не пускать — придумано.
- Курсы, кроме магазинов (Спиннингисты на Озере Кулгу, Поплавочники у Лизы — гайды): «Учебник в упаковке» из мусора Пустоши и Разливов, его скрипт сам выдаёт случайный курс; «Параметры» — рецепт из коллекций.

## Радиация и агрессивная среда

- У каждой базы две вилки, днём нижнее число, ночью верхнее (`vitals.radiation`, `vitals.aggression`); в самой базе обеих нет. Цифры локации — на нижней панели: S→C 1001 — пять float погоды (облака, туман, дождь, снег, гроза; сервер шлёт нули, своей погоды у него нет), int радиация, int агрессивная среда. Сервер шлёт его, когда цифры меняются.
- Костюм (вид 33, в одежде) защищает: первое число `basePar` — от радиации, второе — от агрессивной среды (так их подписывает подсказка клиента). Проходит всё сверх защиты и треть остального: радиация 60 и среда 30 в костюме 40/40 — 33,3 и 10 (формула и пример из гайда 1102257736).
- Прошедшая радиация тратит радстойкость. Прошедшие радиация и среда вместе ускоряют голод и жажду (анонс: «чем выше радиация и агрессивность среды на локации, тем больше хочется есть и пить»), на `vitals.environmentHungerPercent`% за единицу (придумано). Что на Разливах и в Дельте радиация небольшая, а среда высокая, — из гайда; сколько радиации там — придумано.

## Смерть

- Жизнь падает без воды и без радстойкости; на нуле персонаж умирает. S→C 905 (пусто): клиент пишет «Игрок умер...», играет звук смерти и через 3 секунды шлёт C→S 905 (int 0). ## Холодильник

- Клик по холодильнику в сцене — C→S 166 (int номер объекта: 1 у доктора в Убежище, 0 на базах 3, 4, 6, 7, 8), клиент при этом опускает чёрную шторку. Ответ S→C 166 и 1310, снимающий шторку. В 166: int холодильник, int мест, затем записи рыбы как в садке (175). Слева окно показывает садок в работе, справа — рыбу на льду.

Карточку сервер забирает сам (181 или 190). В системную вкладку чата сервер пишет, сколько теперь мест в холодильнике этой базы. Квестовые значения персонажа (имя → число) хранятся в таблице `quest_values`.

## Почта

- Почтовый ящик на базе — C→S 1600 (int 0). S→C 1600: int 0, затем письма до конца: long id, string от кого, string тема, дата, bool есть вложения, bool прочитано; S→C 1601 (пусто) открывает окно со списком.
- Клик по письму — C→S 1610 (long письмо), клиент сам помечает его прочитанным. S→C 1610: long id, long отправитель (клиент даёт «Ответить», когда он больше 10; сервер шлёт id отправителя, но не меньше 11), string от кого, string тема, дата, string текст, string вложения через `;`: `money=N` (в сотых), `weapon=предмет`. Предмет клиент должен уже знать, поэтому сначала приходит 181 с владельцем 0: клиент запоминает вещь, но в сумки её не кладёт.
- «Забрать вложения» — C→S 1620 (long письмо): деньги на счёт, вещи — как есть (с износом и деталями) в свободные ячейки своих страниц. Что не поместилось, остаётся в письме, и список приходит заново. Итог — строка в системную вкладку чата.
- «Удалить» — C→S 1640 (long письмо): письмо с вложениями клиент не удаляет сам, сервер тоже. «Удалить все» — C→S 1650: удаляются письма без вложений, список приходит заново.
- «Написать»: «Найти» — C→S 45 (string имя), S→C 45: персонажи, в имени которых есть эта строка (`mail.mostFound`): long id, string имя, int база, int локация (у тех, кто не в игре, — 0). «Отправить» — C→S 1660: string кому, string тема, string текст, long деньги, int n, n × long предмет. S→C 1660 (int): 0 отправлено, 1 получатель не найден, 2 не хватает денег, 3 ошибка (уровень ниже `mail.minLevel`), 4 предметы не найдены (не свои, выброшенные или личные — `isPersonal`), 5 самому себе.
- Стоимость — как в форме клиента: 10 + десятая часть денег + 100 за предмет (в сотых), с VIP вдвое меньше. Писать можно с 5-го уровня (строка клиента `newletter`).
- Письма и их вещи хранятся отдельно от персонажей (таблицы `letters` и `letter_items`), поэтому получатель в игре и отправитель не перезаписывают друг друга. Получатель в игре узнаёт о письме на следующем такте (S→C 275, «Вам пришло письмо»), при входе — если есть непрочитанные.

## Статистика и рекорды

- Вкладка «Статистика» — S→C 1150, по строке на вид до конца: int вид, long выловлено, long общий вес, long личный рекорд, float мастерство (100 — это 100%), int венков 0-3. Считается каждая вытащенная рыба, отпущенная тоже (таблица `catches`). Мастерство и три венка — из гайдов 844577800 и 1102257736, сколько рыбы на каждый венок придумано (`mastery.catches`). Каждый венок умножает вес вида при выборе рыбы на 1 + 3% (`mastery.bitePercent`, из гайдов): вид клюёт чаще, и общий шанс поклёвки чуть растёт. И поднимает шанс карточки этой рыбы на 5%.
- Вкладка «Рекорды» — S→C 40 на запрос с 0: int вид, long владелец, string имя, int граммы, int база, int локация, int наживка (клиент рисует её значок, поэтому это всегда настоящий предмет). В оригинале там были рекорды всего сервера, здесь — свои.
- Рекорды теперь помнят локацию и наживку. Старые рекорды без них показывают локацию «База», а при входе засчитываются в статистику как одна выловленная рыба рекордного веса.

## Репутация

- Вкладка «Репутация» — S→C 30, по строке на фракцию до конца: int фракция, int уровень, int очки внутри уровня. Сколько нужно на уровень, клиент считает сам по своей таблице: с уровня n на n+1 нужно `startA + startB * kfB * n`. Эти числа и число уровней каждой фракции взяты из ресурса `RepFractions` в `resources.assets` и лежат в `reputation.factions`. Сервер хранит очки фракции за все уровни вместе (таблица `reputation`).
- О каждом начислении сервер пишет S→C 307 (int фракция, int, int, int очки — средние два клиент пропускает). Перед первым начислением шлёт 305 (int фракция, «Открыта новая фракция»), а на каждом новом уровне — 306 (int фракция, int уровень).
- Генератор в Убежище — NPC 2, его диалог `2.lng`. Узел 1 показывает, сколько биотоплива (1170) с собой (`[cnt]`), и предлагает сдать всё, 1 или 10 штук. 80 очков Убежища за штуку — из гайда 844577800. Ответ «Сдать единицу фарша» есть в файле, но ни в одном гайде, поэтому не показывается.
- Отпущенная рыба даёт репутацию фракции базы. Засчитывается и рыба из садка, и рыба, отпущенная сразу из окна вылова. Что очков больше за тяжёлую рыбу — из гайдов; сколько именно (1 + 1 за каждый кг) — придумано (`reputation.release`). Какой базе какая фракция — `reputation.baseFactions`.
- Навыки «Вклад» (180 «Поплавок», 190 «Спиннинг», 192 «Донный») за каждую вытащенную рыбу на удилище своего вида дают очки союза. По уровню навыка: 2 очка + 1 за каждые 12 кг, 3 + 1/6 кг, 4 + 1/4 кг, 5 + 1/3 кг, 6 + 1/2,4 кг (гайд 1102257736). Очки идут, только когда союз открыт — у персонажа уже есть его репутация: после задания союза с доски у спиннингистов и доночников и после линейки Лизы у поплавочников (гайд); спиннингистов открывает и линейка Паши.
- Каждый уровень репутации базы добавляет на ней +10% опыта за рыбу, +4% к шансу лута, +4% удачи (доля трофеев) и +5% к шансу карточки базы (гайды 844577800 и 1102257736, `reputation.perLevel`).
- Задания с доски на вкладке «Опыт и реп.» дают репутацию базы (см. «Доска заданий»).
- Задания союзов (`board.unions`): на той же вкладке, кроме заданий базы, `offers` заданий союза на его базах. Рыба — из локаций базы, которую ловят снасти союза: спиннингисты (Озеро Кулгу) — виды, которые берут искусственные приманки (вид предмета 12), и наживка задания на вес — тоже такая приманка; доночники (Разливы) — донные виды. Награда — опыт, репутация союза за каждый цвет и у спиннингистов жетон кладовщика (гайд: задания спиннингистов на Озере дают жетон кладовщика и репутацию). Из гайдов и анонсов — Озеро у спиннингистов и донные снасти за репутацию на Разливах; число заданий и очки придуманы.
- Рецепты за репутацию — те же товары автоматов с требованием в `reputation` (`config/shops.json`).
- Товары за репутацию: `reputation` в `config/shops.json`, предмет → [фракция, уровень]. В данных клиента требований нет, их проверял сервер. По анонсу «все репутационные товары видны сразу»: такие вещи стоят в автомате с флагом «нельзя купить» (последний bool записи 1300), а покупка отвечает 1310 `none=0` и строкой в чат, какая репутация нужна. Из гайда 1102257736 — что автомат спиннингистов Озера Кулгу продаёт за репутацию (Щука-Т1, РодРолл-18, ЩукаРолл-I, ЛакЛайн, ЩукаЛайн-I, рецепты «Райва», «Норд», крупных блёсен) и что на Пруду без неё продаются колбы и Бамбук-4; из анонсов — «Рубикон» у поплавочников и донные снасти Б за репутацию Донной гильдии на Разливах. Уровни, старшие снасти «Щука» (Т2, Т3), карповые Лизы, донки Б и товары фракций баз — придуманы. В Убежище с репутацией Убежища продаются Бамбук-3, РодРолл-4, Мононить-спец, Импульс-II, костюм рыбака (уровень 1), Импульс-III (2) и костюм сталкера (3): Василич обещает за репутацию «более качественное оборудование в торговых автоматах», какое — придумано; требование одно на вещь для всех баз, поэтому выбраны вещи, которые продаёт только Убежище.
- Ещё нет: +10% опыта за уровень союзов (гайд 844577800 говорит так о каждой фракции).

## Настройки

- `config/settings.json`: порт, персонаж, шансы клёва, вываживание, базы (уровни, цена перехода), стартовый набор.
  Файл допускает комментарии. Применяется после перезапуска сервера.
- `config/settings.local.json` (необязательный, в git не попадает) кладётся поверх `settings.json`: его ключи
  заменяют те же ключи на любой глубине. Для настроек одной машины, например
  `{ "progression": { "experiencePerFish": 4 } }`.
- `config/fish.json`: виды рыбы и список видов по локациям. Генерируется `tools/gen_fish.py`, можно править руками.
- Другой каталог настроек: `--config <папка>`.
- `travel.enforceLevels` закрывает базы ниже их `minLevel`; `false` открывает все базы сразу.
- VIP: патент покупается в окне VIP (C→S 220, int 0 → S→C 21 с новым балансом эргов, 260 со значком и датой окончания, 220 int 1; при нехватке эргов 220 int -1, «Нехватка средств»). Срок хранится в `characters.vip_until` (секунды Unix), продление добавляет дни к остатку. Колонка `characters.vip` — VIP навсегда, ставится руками. Значок VIP открывает кнопки «Узнать цены» и «Продать всё»; когда срок выходит, клиент убирает его сам. Бонусы из окна VIP в клиенте (`vip` в настройках): продажа рыбы +50% (вторая сумма в «Получено X+Y»), опыт за рыбу +50% (в окне вылова и в 155), шанс лута +10% от самого шанса (придумано, что от шанса), +1 очко опыта навыку на изучении за 2 минуты онлайн, перерыв между ежедневными заданиями доски и стоимость письма вдвое меньше (`vip.taskWaitPercent`, `vip.mailCostPercent`; «ожидание задания» — по-нашему, это перерыв ежедневных). В 155 третье число теперь доля опыта в навыки.
- `attributes` задаёт действие Удачи и Образования, в клиенте их никто не читает.
- `shop.enforceLevels` не даёт купить предмет раньше его уровня.
- `bags` задаёт вкладки сумок, размер склада и цену новых ячеек, `fishing.baitPerCatch` — расход наживки.

## Бэклог

Порядок: репутация, навыки, затем остальное. Перед тем как придумывать правила и числа для пункта, сначала искать их в гайдах игроков и архивах; придуманное выносить в настройки.

- Подсказки предметов иногда перестают рисоваться (белое пустое окно у всех вещей, раньше работали): что их ломает, не найдено, ошибок в логе клиента нет.
- Холодильник: портится ли рыба на льду и сколько мест было в оригинале без карточек — не найдено.
- Доска: задания на предметы (типы 4/5) клиент нарисует, но только с текстом с `[wtemplid]`, а таких текстов у разделов доски в `QTask.xml` нет — делать нечем. Сдать рыбу из садка можно только в диалоге NPC (`[userfish]`, 72 с id рыбы → 65), окна доски и списка заданий ничего такого не шлют.
- Аукцион и артели: окна пустые, других игроков на сервере нет.
- Советник: какую деталь снасти купить, наживки, которых у персонажа нет, и лучшее время суток сразу.
